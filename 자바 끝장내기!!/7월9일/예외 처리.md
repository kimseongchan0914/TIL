# 3일차 정리 — 예외 처리 (Exception Handling)

---

## 예외란?
프로그램 실행 중에 발생하는 **예상치 못한 문제 상황**.
처리하지 않으면 프로그램이 그 자리에서 죽는다.

```java
int[] arr = {1, 2, 3};
System.out.println(arr[5]);   // 인덱스 5는 없음 → ArrayIndexOutOfBoundsException
```

---

## 기본 문법 — try / catch / finally

```java
try {
    int[] arr = {1, 2, 3};
    System.out.println(arr[5]);        // 위험할 수 있는 코드
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("잘못된 인덱스입니다!");  // 문제 생기면 실행
} finally {
    System.out.println("무조건 실행됩니다.");     // 성공/실패 관계없이 실행
}
```

| 블록 | 역할 |
|---|---|
| `try` | 위험할 수 있는 코드를 넣는 곳 |
| `catch` | 문제가 생겼을 때 대신 실행할 코드 |
| `finally` | 성공하든 실패하든 **무조건** 실행 (주로 자원 정리: 파일/DB 닫기) |

---

## 예외의 두 종류 (핵심)

### 1. Checked Exception (체크 예외)
- 컴파일러가 처리를 **강제**한다 → try-catch 하거나 `throws`로 넘겨야 컴파일됨
- 주로 **외부 요인**과 관련 (파일, DB, 네트워크)
- 예: `IOException`, `SQLException`

### 2. Unchecked Exception (언체크 예외)
- 컴파일러가 강제하지 **않는다** (`RuntimeException`의 자식들)
- 처리 안 해도 컴파일은 됨 (실행 중 터지면 프로그램 종료)
- 주로 **코드 실수**로 발생
- 예: `NullPointerException`, `ArrayIndexOutOfBoundsException`, `IllegalArgumentException`

### 비교표
| | Checked | Unchecked |
|---|---|---|
| 처리 강제? | 예 (컴파일러가 강제) | 아니오 |
| 대표 예시 | IOException, SQLException | NullPointerException, IllegalArgumentException |
| 언제 발생 | 외부 요인 (파일, DB, 네트워크) | 주로 코드 실수 |
| 상속 뿌리 | Exception | RuntimeException |

## throws — 예외를 호출한 쪽으로 떠넘기기
```java
public void readFile() throws IOException {   // "나 이 예외 안 처리할게, 부르는 쪽이 처리해"
    // 파일 읽기 코드
}
```
`try-catch`로 직접 처리하지 않고, 이 메서드를 호출한 쪽에게 처리 책임을 넘긴다.

호출한 쪽에서 처리:
```java
public void doSomething() {
    try {
        readFile();   // IOException을 던질 수 있으니
    } catch (IOException e) {
        System.out.println("파일 읽기 실패");   // 여기서 처리
    }
}
```

**왜 떠넘길까?** 예외를 어디서 처리할지는 상황에 따라 다르다. 보통 **그 예외에 어떻게 대응할지 아는 곳**에서 처리하는 게 맞다. 낮은 레벨(파일 읽는 메서드)은 에러 발생만 알리고, 실제 대응(사용자 알림 등)은 상위에서 하는 게 깔끔하다.

### throw vs throws (자주 헷갈림)
| | throw | throws |
|---|---|---|
| 위치 | 코드 안 | 메서드 선언부 |
| 의미 | 예외를 **지금 던진다** | 예외를 **던질 수 있다** (표시) |
| 예시 | `throw new XxxException()` | `void m() throws IOException` |

## 커스텀 예외 (직접 만드는 예외)
실무에서는 상황에 맞는 예외를 직접 정의해서 쓴다.

```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}
```

사용:
```java
public User findUser(Long id) {
    User user = userRepository.findById(id);
    if (user == null) {
        throw new UserNotFoundException("회원을 찾을 수 없습니다. id=" + id);
    }
    return user;
}
```

- `extends RuntimeException` → 이 예외는 **Unchecked**가 된다 (try-catch 강제 안 됨)
- `super(message)` → 부모에게 에러 메시지 전달
- `throw` → "예외를 **지금 던진다**" (선언부에 붙는 `throws`와 구분)

**장점**
- `RuntimeException` 하나로 뭉뚱그리는 것보다, `UserNotFoundException`처럼 이름만 봐도 문제를 바로 알 수 있다.
- 실무에서는 이 커스텀 예외를 `@ControllerAdvice`로 잡아 "404 응답 + 에러 메시지"로 깔끔하게 처리한다 (3주차 학습 예정).
