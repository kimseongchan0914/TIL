# SOLID 원칙 정리 (객체지향 설계 핵심 개념)

## 1. SOLID란 무엇인가

SOLID는 객체지향 프로그래밍에서 유지보수성과 확장성을 높이기 위해 제시된 5가지 설계 원칙이다.  
소프트웨어가 커지고 복잡해질수록 코드 변경이 어려워지고, 작은 수정이 전체 시스템에 영향을 주는 문제가 발생한다.  
SOLID는 이러한 문제를 해결하기 위해 등장한 설계 기준이다.

각 원칙은 다음과 같다.

- S: Single Responsibility Principle (단일 책임 원칙)
- O: Open/Closed Principle (개방-폐쇄 원칙)
- L: Liskov Substitution Principle (리스코프 치환 원칙)
- I: Interface Segregation Principle (인터페이스 분리 원칙)
- D: Dependency Inversion Principle (의존 역전 원칙)

이 다섯 가지 원칙은 서로 독립적이면서도 함께 적용될 때 가장 큰 효과를 낸다.

---

## 2. SOLID의 목적

SOLID의 핵심 목적은 다음과 같다.

- 변경에 유연한 코드 작성
- 기능 확장이 쉬운 구조 설계
- 코드 간 결합도를 낮추기
- 재사용성과 테스트 용이성 향상

즉, "잘 동작하는 코드"를 넘어서 "오래 유지할 수 있는 코드"를 만드는 것이 목적이다.

---

## 3. SRP (Single Responsibility Principle)

단일 책임 원칙은 하나의 클래스는 하나의 책임만 가져야 한다는 원칙이다.  
여기서 말하는 책임은 단순히 기능의 개수가 아니라 "변경의 이유"를 의미한다.

하나의 클래스가 여러 책임을 가지면, 서로 다른 이유로 인해 동시에 수정될 가능성이 높아진다.  
이 경우 한 기능을 수정하다가 다른 기능에 영향을 주는 문제가 발생한다.

예를 들어 사용자 정보를 저장하고 이메일을 보내는 기능이 하나의 클래스에 같이 있다면,  
데이터베이스 로직 변경과 이메일 로직 변경이 하나의 클래스에서 동시에 발생하게 된다.

이러한 문제를 해결하기 위해 역할별로 클래스를 분리해야 한다.

SRP를 적용하면 다음과 같은 효과가 있다.

- 코드 수정 시 영향 범위 최소화
- 가독성 향상
- 테스트 단위가 명확해짐

Spring에서 Controller, Service, Repository를 나누는 것도 SRP를 적용한 대표적인 사례이다.

---

## 4. OCP (Open/Closed Principle)

개방-폐쇄 원칙은 기존 코드를 수정하지 않고 기능을 확장할 수 있어야 한다는 원칙이다.  
즉, 새로운 기능을 추가할 때 기존 코드를 변경하는 것이 아니라 새로운 코드를 추가하는 방식으로 확장해야 한다.

예를 들어 결제 시스템에서 카드 결제, 카카오페이 결제 등이 있다고 가정하면,  
if-else 문으로 분기 처리하는 방식은 새로운 결제 수단이 추가될 때마다 기존 코드를 수정해야 한다.

이 문제를 해결하기 위해 인터페이스와 다형성을 활용한다.

공통 인터페이스를 정의하고, 각 기능을 별도의 클래스로 구현하면  
새로운 기능이 추가될 때 기존 코드를 수정하지 않고 새로운 클래스를 추가하기만 하면 된다.

OCP를 적용하면 다음과 같은 장점이 있다.

- 기존 코드 안정성 유지
- 기능 확장 시 리스크 감소
- 코드 변경 비용 감소

이 원칙은 플러그인 구조나 전략 패턴과도 밀접한 관련이 있다.

---

## 5. LSP (Liskov Substitution Principle)

리스코프 치환 원칙은 자식 클래스는 부모 클래스를 완전히 대체할 수 있어야 한다는 원칙이다.  
즉, 부모 타입을 사용하는 코드에서 자식 객체를 넣어도 정상적으로 동작해야 한다.

이 원칙이 깨지는 대표적인 경우는 상속 관계가 잘못 설계된 경우이다.

예를 들어 Bird 클래스에 fly() 메서드가 있고, Penguin이 이를 상속받는다면  
펭귄은 날 수 없기 때문에 fly()를 제대로 구현할 수 없다.  
이 경우 자식 클래스가 부모의 계약을 깨는 상황이 발생한다.

이러한 문제를 해결하기 위해서는 상속 구조를 재설계해야 한다.  
공통 기능만 부모 클래스에 두고, 특화된 기능은 별도의 계층으로 분리해야 한다.

LSP를 지키면 다음과 같은 장점이 있다.

- 다형성의 안정성 확보
- 예측 가능한 코드 동작
- 상속 구조의 일관성 유지

결론적으로 "is-a 관계가 성립하는지"를 항상 고민해야 한다.

---

## 6. ISP (Interface Segregation Principle)

인터페이스 분리 원칙은 클라이언트가 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야 한다는 원칙이다.

하나의 큰 인터페이스에 여러 기능을 넣으면, 이를 구현하는 클래스는 필요하지 않은 메서드까지 구현해야 하는 문제가 발생한다.

예를 들어 Animal 인터페이스에 fly와 swim이 모두 정의되어 있다면,  
날지 못하는 동물도 fly 메서드를 구현해야 한다.

이 문제를 해결하기 위해 인터페이스를 역할 단위로 나누어야 한다.

작고 구체적인 인터페이스로 분리하면 각 클래스는 필요한 기능만 구현하게 된다.

ISP를 적용하면 다음과 같은 효과가 있다.

- 불필요한 의존성 제거
- 코드 유연성 증가
- 변경 영향 최소화

이 원칙은 "인터페이스는 작을수록 좋다"라는 설계 철학으로 이어진다.

---

## 7. DIP (Dependency Inversion Principle)

의존 역전 원칙은 고수준 모듈이 저수준 모듈에 의존하지 않고,  
둘 다 추상화(인터페이스)에 의존해야 한다는 원칙이다.

기존에는 상위 클래스가 하위 클래스의 구체 구현에 직접 의존하는 구조가 많았다.  
이 경우 하위 클래스가 변경되면 상위 클래스도 함께 수정해야 하는 문제가 발생한다.

이를 해결하기 위해 인터페이스를 도입하고,  
상위 클래스는 구체 클래스가 아니라 인터페이스에 의존하도록 설계한다.

또한 객체 생성은 외부에서 주입받도록 하여 결합도를 낮춘다.

DIP는 Spring의 DI(의존성 주입)와 밀접한 관련이 있다.

이 원칙을 적용하면 다음과 같은 장점이 있다.

- 클래스 간 결합도 감소
- 테스트 용이성 증가 (Mock 객체 사용 가능)
- 유연한 구조 설계

결론적으로 "구현이 아니라 역할에 의존하라"는 것이 핵심이다.

---

## 8. SOLID 원칙의 관계

SOLID 원칙은 각각 독립적으로 보이지만 실제로는 서로 긴밀하게 연결되어 있다.

- SRP는 클래스의 역할을 명확하게 나눈다
- OCP는 확장 가능한 구조를 만든다
- LSP는 올바른 상속 관계를 유지한다
- ISP는 인터페이스를 세분화한다
- DIP는 의존성을 추상화한다

이 원칙들이 함께 적용되면 다음과 같은 구조가 만들어진다.

- 변경에 강한 코드
- 확장이 쉬운 구조
- 테스트 가능한 설계
- 유지보수가 용이한 시스템

---

## 9. 최종 정리

SOLID는 단순한 이론이 아니라 실무에서 코드 품질을 결정하는 중요한 기준이다.  
특히 Spring과 같은 프레임워크는 SOLID 원칙을 기반으로 설계되어 있기 때문에  
이를 이해하면 프레임워크 구조를 더 깊이 이해할 수 있다.

핵심을 정리하면 다음과 같다.

- SRP: 하나의 클래스는 하나의 책임만 가진다
- OCP: 기존 코드를 수정하지 않고 확장한다
- LSP: 자식 클래스는 부모를 대체할 수 있어야 한다
- ISP: 인터페이스는 작고 구체적으로 나눈다
- DIP: 구현이 아니라 추상에 의존한다

결론적으로 SOLID는 "변경에 강하고 확장에 유리한 객체지향 설계의 기준"이다.
