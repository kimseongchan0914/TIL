# 비밀번호 암호화 (Password Hashing)

## 핵심 요약

> 비밀번호 보안의 핵심은 세 가지다.
> 1. **단방향 해싱** — 되돌릴 수 없게 만든다
> 2. **솔트(Salt)** — 사전 공격을 막는다
> 3. **작업 강도(Work Factor)** — 무차별 대입을 막는다
>
> BCrypt는 이 세 가지를 한 번에 처리해주고, Spring Security의 `PasswordEncoder`가 이를 감싸 `encode`와 `matches` 두 메서드로 간단히 쓸 수 있게 해준다.

---

## 1. 암호화(Encryption)가 아니라 해싱(Hashing)이다

흔히 "비밀번호 암호화"라고 부르지만, 실제로 쓰는 기술은 **해싱**이다. 둘은 완전히 다르다.

| 구분 | 암호화(Encryption) | 해싱(Hashing) |
|------|-------------------|---------------|
| 방향 | 양방향 (복호화 가능) | **단방향 (복호화 불가)** |
| 목적 | 감췄다가 다시 원문으로 | 원문 확인만, 되돌리기 불가 |
| 예시 | AES, RSA | BCrypt, SHA-256 |

비밀번호는 **되돌릴 필요가 없다.** 서버조차 사용자의 원래 비밀번호를 알 필요가 없다. 로그인할 때 "입력한 비밀번호를 똑같이 해싱했을 때 저장된 값과 같은가?"만 확인하면 되기 때문이다. 그래서 되돌릴 수 있는 암호화보다, 아예 되돌릴 수 없는 해싱이 더 안전하다.

---

## 2. 왜 평문 저장은 절대 안 되는가

DB에 `password = "1234"`처럼 그대로 저장하면, DB가 한 번 털리는 순간 모든 사용자의 비밀번호가 그대로 노출된다. 사람들은 같은 비밀번호를 여러 사이트에 재사용하기 때문에, 피해가 그 사이트 하나로 끝나지 않는다.

---

## 3. 단방향 해시의 동작

```
"myPassword123"  →  [해시 함수]  →  "$2a$10$N9qo8uLOickgx2ZMRZoMy..."
```

같은 입력은 항상 같은 출력을 내지만, 출력에서 입력을 역산하는 것은 불가능하다.

### 저장과 검증 흐름

```
[회원가입 - 저장]
비밀번호 입력  →  해시 함수  →  해시값을 DB에 저장

[로그인 - 검증]
비밀번호 입력  →  같은 해시 함수  →  새 해시값 계산
                                        ↓
                    DB에 저장된 해시값과 비교
                                        ↓
                    일치 → 로그인 성공 / 불일치 → 실패
```

핵심은 서버가 원래 비밀번호를 저장하지 않고 **해시값끼리만 비교**한다는 점이다.

---

## 4. 문제 1 — 레인보우 테이블 공격과 솔트(Salt)

SHA-256 같은 함수는 같은 입력이면 항상 같은 출력이라, 공격자가 "흔한 비밀번호 → 해시값" 사전(레인보우 테이블)을 미리 만들어두면 해시값만 보고 원문을 역추적할 수 있다.

이를 막는 것이 **솔트**다. 사용자마다 랜덤한 문자열을 비밀번호에 섞어서 해싱한다.

```
사용자 A: "1234" + 솔트("x8Kq")  →  완전히 다른 해시
사용자 B: "1234" + 솔트("mP2v")  →  또 다른 해시
```

같은 비밀번호 `1234`를 써도 저장된 해시값이 서로 달라진다. 미리 만들어둔 사전이 무력화된다. BCrypt는 이 솔트를 **해시 결과 안에 자동으로 포함**시켜 저장해준다.

---

## 5. 문제 2 — 무차별 대입과 작업 강도(Work Factor)

요즘 GPU는 초당 수십억 개의 해시를 계산할 수 있다. 그래서 일부러 **느린** 해시 함수를 쓴다. BCrypt에는 "작업 강도(cost/strength)"라는 값이 있다.

```java
new BCryptPasswordEncoder(10);  // 2^10 = 1024번 반복
new BCryptPasswordEncoder(12);  // 2^12 = 4096번 반복 (4배 더 느림)
```

숫자를 1 올릴 때마다 계산량이 2배가 된다. 정상 로그인은 0.1초 정도라 사람은 못 느끼지만, 공격자가 수십억 개를 시도하려면 현실적으로 불가능한 시간이 걸린다. 하드웨어가 빨라지면 이 숫자를 올려서 방어력을 유지할 수 있다.

---

## 6. Spring Security에서의 사용

### PasswordEncoder 빈 등록

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();  // 기본 strength 10
}
```

### 회원가입 시 저장

```java
String hashed = passwordEncoder.encode(rawPassword);
user.setPassword(hashed);  // "$2a$10$..." 형태로 저장됨
```

### 로그인 검증 시

직접 비교하지 않고 `matches`를 사용한다.

```java
boolean ok = passwordEncoder.matches(rawPassword, user.getPassword());
```

`matches`가 내부적으로 저장된 해시에서 솔트를 꺼내 입력값을 같은 방식으로 해싱한 뒤 비교해준다.

---

## 7. BCrypt 해시값 뜯어보기

저장되는 `$2a$10$N9qo8uLOickgx2ZMRZoMy...`는 다음과 같이 구성되어 있다.

| 부분 | 값 | 의미 |
|------|-----|------|
| `$2a$` | 알고리즘 버전 | BCrypt |
| `10` | 작업 강도 | 2¹⁰ 반복 |
| 다음 22자 | 솔트 | 자동 생성된 랜덤값 |
| 나머지 | 해시 | 실제 결과 |

솔트가 해시값 안에 같이 들어있어서, 별도 컬럼에 솔트를 저장할 필요가 없다는 점이 편리하다.

---

## 8. 참고 — 그 외 해싱 알고리즘

BCrypt 외에도 더 최신 방식이 있다.

- **Argon2** — 2015년 패스워드 해싱 경진대회 우승 알고리즘. 메모리 사용량까지 조절 가능해 GPU 공격에 강하다.
- **scrypt** — 메모리를 많이 쓰도록 설계되어 무차별 대입에 강하다.
- **PBKDF2** — 오래되었지만 표준으로 널리 쓰인다.

Spring Security는 이들을 위한 `Argon2PasswordEncoder`, `SCryptPasswordEncoder`, `Pbkdf2PasswordEncoder`도 제공한다.

## 최종 정리

| 개념 | 역할 |
|------|------|
| 단방향 해싱 | 비밀번호를 되돌릴 수 없게 저장 |
| 솔트(Salt) | 사용자마다 다른 값을 섞어 사전 공격 방어 |
| 작업 강도(Work Factor) | 일부러 느리게 만들어 무차별 대입 방어 |
| BCryptPasswordEncoder | 위 세 가지를 자동 처리하는 Spring Security 구현체 |
| encode() | 비밀번호를 해싱해 저장 |
| matches() | 입력값과 저장된 해시를 비교 |
