# 지연로딩과 프록시의 관계

## 1. 한 줄 요약

JPA의 지연로딩도 **프록시**로 구현된다. 연관 엔티티를 실제 객체 대신 **프록시 객체**로 넣어두고, 실제로 값이 필요한 순간에 DB 쿼리를 날려 초기화한다.

---

## 2. 즉시로딩 vs 지연로딩

| 종류 | 설정 | 동작 |
|------|------|------|
| **즉시로딩** | `FetchType.EAGER` | 엔티티 조회 시 연관 엔티티도 **바로 함께** 조회 |
| **지연로딩** | `FetchType.LAZY` | 연관 엔티티는 **프록시**로 두고, 실제 사용 시점에 조회 |

**기본값**
- `@ManyToOne`, `@OneToOne` → **EAGER** (기본)
- `@OneToMany`, `@ManyToMany` → **LAZY** (기본)
- 실무 권장: **전부 LAZY로 두고 필요할 때 fetch join**

---

## 3. 지연로딩 동작 원리

```java
@Entity
class Member {
    @ManyToOne(fetch = FetchType.LAZY)
    private Team team; // 실제로는 Team의 프록시 객체가 들어있음
}
```

```java
Member member = em.find(Member.class, 1L);
// 이 시점: team은 프록시 객체 (DB 조회 X)

member.getTeam();          // 아직 프록시, 쿼리 안 나감
member.getTeam().getName(); // ← 이때 SELECT 쿼리 실행! (프록시 초기화)
```

---

## 4. 프록시 초기화 흐름

```
1. member.getTeam().getName() 호출
2. 프록시가 "나 아직 초기화 안 됐네?" 감지
3. 영속성 컨텍스트에 실제 엔티티 요청
4. DB에 SELECT 쿼리 실행
5. 실제 Team 엔티티 생성 → 프록시가 참조 연결
6. getName() 결과 반환
```

한 번 초기화되면 이후엔 쿼리 안 나가고 캐시된 값 사용.

---

## 5. Spring AOP 프록시 vs JPA Lazy 프록시

**개념이 똑같다:** "원본을 감싸서, 필요할 때 진짜 동작을 수행한다."

| 구분 | 목적 | 진짜 동작 시점 |
|------|------|---------------|
| **AOP 프록시** (@Transactional) | 부가 기능(트랜잭션) 삽입 | 메서드 호출 시 |
| **Lazy 프록시** (JPA) | DB 조회를 최대한 미룸 | 값에 실제 접근할 때 |

둘 다 **프록시**라는 공통 개념. 이게 "지연로딩과 프록시의 관계"의 핵심.

---

## 6. LazyInitializationException (가장 중요!)

### 언제 발생?
영속성 컨텍스트(트랜잭션)가 **끝난 뒤에** 프록시를 초기화하려 할 때.

```java
@Transactional
public Member getMember(Long id) {
    return em.find(Member.class, id);
} // ← 여기서 트랜잭션 종료, 영속성 컨텍스트 닫힘

// Controller에서:
member.getTeam().getName();
// ❌ LazyInitializationException!
// 프록시를 초기화하려는데 영속성 컨텍스트가 이미 닫힘
```

### 왜?
프록시 초기화는 DB 조회가 필요한데, 영속성 컨텍스트가 닫히면 조회할 방법이 없음.

---

## 7. 해결 방법 4가지

### (1) Fetch Join (가장 권장)
쿼리에서 연관 엔티티를 미리 함께 조회.
```java
@Query("SELECT m FROM Member m JOIN FETCH m.team WHERE m.id = :id")
Member findWithTeam(@Param("id") Long id);
```

### (2) @EntityGraph
```java
@EntityGraph(attributePaths = {"team"})
Optional<Member> findById(Long id);
```

### (3) DTO로 필요한 것만 조회
```java
@Query("SELECT new com.example.MemberDto(m.name, t.name) " +
       "FROM Member m JOIN m.team t")
List<MemberDto> findAllDto();
```

### (4) OSIV (Open Session In View)
- `spring.jpa.open-in-view=true` (기본 켜짐)
- 영속성 컨텍스트를 View 렌더링까지 유지 → 예외 안 남
- **단점:** DB 커넥션을 오래 물고 있어 성능 이슈 → 실무에선 끄고 fetch join 권장

---

## 8. N+1 문제 (지연로딩 관련 필수)

지연로딩 상태에서 리스트를 순회하며 연관 엔티티에 접근하면, 각 요소마다 쿼리가 나감.

```java
List<Member> members = memberRepository.findAll(); // 쿼리 1번
for (Member m : members) {
    m.getTeam().getName(); // 각 member마다 쿼리 N번 → 총 1 + N번
}
```

**해결:** Fetch Join, `@EntityGraph`, `@BatchSize`

---

## 9. 최종 요약

- 지연로딩 = 연관 엔티티를 **프록시**로 두고 사용 시점에 조회
- AOP 프록시와 원리 개념 동일 (원본 감싸서 필요할 때 진짜 동작)
- 영속성 컨텍스트 밖에서 초기화 → **LazyInitializationException**
- 해결: **Fetch Join** / `@EntityGraph` / DTO 조회
- **N+1 문제** 주의
